## 1. What it is

A threat actor wears many masks online — different handles, on different markets. But the
person behind them keeps making the same small public mistakes: the same signing key, the
same wallet, the same writing habit, the same activity rhythm. PRAHARI collects those
mistakes from **public** sources, works out which masks are the same actor, and states how
sure it is.

An **actor** is the thing under investigation. A **persona** is one handle on one
marketplace. The entire system exists to decide which personas belong to the same actor, to
say how confident that is, and to show why.

### Three things that make it different

**1. A score that survives cross-examination.**
Stack five correlated signals naively and you get 0.999 — false certainty. PRAHARI converts
each signal to a likelihood ratio, **collapses them by root cause** so one fact cannot be
counted five times, and **dampens each by its measured reliability**. The same evidence
yields **0.84**.

**2. A record nobody can quietly edit.**
Every analyst action is canonically serialised, keccak-256 hashed, chained to its
predecessor and Ed25519-signed. Each case's Merkle root is anchored on Polygon Amoy at zero
gas — **32-byte hashes only, never PII**. One record verifies against the root without
disclosing the rest of the case.

**3. An honest network-layer demo.**
PRAHARI stands up its **own** ephemeral Tor hidden service and its **own** client, then
cross-correlates timing at both ends to show that timing alone links a visitor to a service
— the real principle behind onion de-anonymisation, run legally on infrastructure it owns.

## 3. The six stages

Data flows one way. Each stage has a single job and hands the next a typed contract.

```
COLLECT   ──▶  EXTRACT  ──▶  FOUR ENGINES   ──▶   EVIDENCE FUSION
public data    entities      infra · identity     LR per signal, grouped

Agora CSV      onion/city    each emits Signals   by reliability
OSINT feeds    contraband    with a root label    ↓
crt.sh/Shodan  handle/email                       PairScore + trail
mempool/Etherscan                                 ↓
                                                  STAGE 4
                                                  GEO-ATTRIBUTION
                                                  v1 geofence, UNCHANGED
                                                  ↓
                                                  STAGE 5
                                                  WORKBENCH + AUDIT
                                                  hash chain · Ed25519
                                                  Merkle root → chain
                                                  CSV / JSON / PDF export
```

| Stage | What happens |
|---|---|
| **0 · Collect** | Public data only: DNM archives, the Kaggle Agora 2014–15 dump, OSINT feeds (Hacker News, Google News RSS, Reddit JSON), certificate transparency via certspotter and crt.sh, Shodan InternetDB, mempool.space and Etherscan. 1,000-row fixtures ship in the repo so the demo never needs a full download. |
| **1 · Extract** | Regex + gazetteer + spaCy pull PGP fingerprints, wallets (BTC/ETH/XMR), onion v3 addresses, handles, emails, cities and contraband terms out of listing text. Hinglish is a first-class input, not an afterthought. |

| **4 · Geo-attribution** | **v1, frozen.** `isInJabalpurZone()` remains the breach predicate, driven by real haversine distance against the MP gazetteer only. Six invariants in `docs/AUDIT_V1.md` §5 hold it in place. v2 extends it in SANGAM; it never rewrites it. |

### The trust boundary

The browser **never** talks to the engine directly. Every call goes through a server-side
proxy at `/api/engine/[...path]` with a strict allowlist, so the engine URL and any key never
reach the client. `ENGINE_URL` is deliberately **not** prefixed `NEXT_PUBLIC_` so Next cannot
inline it into a client bundle — and a pinned test (INV-2) fails the build if a third reader
of that variable appears.

| Runs in | What it holds | What it must never hold |
|---|---|---|
| **Browser** | React UI, zustand stores, Leaflet/MapLibre, localStorage records | No API key. No engine URL. No private key. |
| **Next server** | NextAuth, the read proxy, the separate admin proxy, `NEXTAUTH_SECRET`, `PASSWORD_PEPPER`, `ENGINE_SERVICE_SECRET` | Sole path to the engine. |
| **FastAPI engine** | Ingest, extract, four engines, fusion, ledger, anchoring, `ANCHORER_KEY`, DB credentials | Not exposed to the browser. |
| **Polygon Amoy** | `anchor(bytes32 root, bytes32 caseRef, uint32 leafCount)` | **32-byte hashes only.** No handle, wallet, name or text. |

**Proxy behaviour worth knowing.** Fusion and audit routes do real computation, and Render's
free plan sleeps. One attempt cannot both fail fast on a real outage and survive a
77-second cold start, so the proxy makes two: the first ends at 45 s having woken the
instance, the retry lands on a warm engine at 60 s. Only `GET` is retried — replaying a
`POST` that seals the ledger and anchors on chain is worse than an honest timeout. A double
timeout renders as *"engine is waking"*, never *"offline"*.

## 4. Five signal families

Six roots exist in the model; five carry live signals today. Colour is the product's own
semantic registry — `web/lib/signals.ts` defines the hexes once and no skin may redefine
them, because in the graph colour *is* the entity type and on the trail colour *is* the
signal root.

| Root | Colour | What links two personas | Reliability `r` | Why that number |
|---|---|---|---|---|
| `identity_key` | `#e8503a` red | A reused PGP signing key across handles | **0.9** | A signing key is close to control |
| `infra` | `#9b7fd8` violet | An onion whose TLS certificate names a clearnet host | **0.8** | Shared infrastructure is hard to fake |
| `financial` | `#d9a441` amber | A shared wallet cluster across markets | **0.7** | Wallets are reused, but also shared and mixed |
| `temporal` | `#5b9bd5` blue | Posting rhythm, plus the live Tor timing correlation | **0.5** | Rhythm is suggestive, not probative |
| `linguistic` | `#4fa97e` green | Stylometry — n-grams, function words, punctuation, Hinglish markers | **0.5** | Style is imitable — see the decoy |
| `social` | `#c98bb0` pink | Vouches, co-presence, handle reuse | **0.5** | Vouches and handles are cheap |

Only **hard identifiers** — key and wallet — can form an actor on their own. Soft signals
adjust confidence but never merge two people by accident. Negatives (`mimicry_suspected`,
`llm_rewrite_suspected`) act as a **cap** on the score, not a subtraction: counter-deception,
honestly applied.

### What each engine actually does

**Infrastructure — `engine/engines/infra.py`.** Onion → clearnet pivoting through
third-party indexes only. Certificate transparency logs are published by CAs; Shodan
InternetDB is a scan someone else already ran. Reading an index is not probing a target.
Enforced by `assert_not_onion()` on every outbound URL *and* a network-layer test — not by
anyone remembering to be careful.

**Identity graph — `engine/engines/linkage.py`.** Splink on DuckDB, doing *candidate
generation with a defensible weight*, not the final verdict. m/u probabilities are trained on
labelled data and can be printed and defended: "the model said 0.9" is not an answer in
court; "shared PGP has m = 0.6531, u = 1.70e-05, therefore a Bayes factor of 38,519" is.

**Stylometry — `engine/engines/stylometry.py`.** TF-IDF over character 3–5 grams,
function-word frequencies, type-token ratio, punctuation habits, and Hinglish markers
(romanised-Hindi token ratio, Devanagari presence, -ji / bhai usage). All CPU, no model
download required. Explicitly the weakest evidence in the system, weighted at half a signing
key.

**Behaviour — `engine/engines/behaviour.py`.** When someone posts, not what they write. A
vendor can rewrite listings; changing the hours they are awake is a lifestyle change. It is
its own root rather than folded into linguistic because the two have genuinely different
causes. All histograms in IST, because the jurisdiction is Jabalpur.

## 5. The confidence model

The number the whole project is judged on. Naive evidence stacking assumes every signal is
independent. They are not, and the consequence is not academic — five correlated signals
stack to 0.999, a claim of near-certainty that will not survive cross-examination.

### The three steps

1. **Likelihood ratios.** `LR = s / (1 − s)`. A probability is not evidence strength; the
   ratio is.
2. **Root-cause collapse.** Signals are grouped by *why* they agree, and only the strongest
   survives per root. Two views of one certificate are one fact. This is the step that stops
   double-counting.
3. **Reliability dampening.** `LR_root ^ r`, where r reflects how much that class of evidence
   has earned — independent of how strong any single instance looks.

```
# engine/engine/fusion/score.py

LR_total  = Π over roots of  LR_root ^ r_root
posterior = prior_odds × LR_total
p         = odds / (1 + odds)

prior odds = 1 : 10       — a pair that survived blocking
             1 : 10,000   — a pair that did not
```

Being proposed as a candidate is itself weak evidence, and pretending otherwise would smuggle
in the base rate. Strengths are clamped to `[1e−6, 1−1e−6]` so a single signal can never
assert certainty.

### The worked example — the pitch

Verified by direct computation and frozen as a unit test.
Inputs: `s = [0.78, 0.71, 0.83, 0.69, 0.74]`, `r = [0.9, 0.7, 0.8, 0.5, 0.5]`

| Root | Signal | s | LR = s/(1−s) | r | LR^r |
|---|---|---|---|---|---|
| `identity_key` | PGP fingerprint | 0.78 | 3.5455 | 0.9 | **3.1240** |
| `financial` | shared wallet | 0.71 | 2.4483 | 0.7 | **1.8716** |
| `infra` | cert reuse | 0.83 | 4.8824 | 0.8 | **3.5555** |
| `linguistic` | writing style | 0.69 | 2.2258 | 0.5 | **1.4919** |
| `temporal` | posting rhythm | 0.74 | 2.8462 | 0.5 | **1.6871** |

```
LR_total       = 3.1240 × 1.8716 × 3.5555 × 1.4919 × 1.6871 = 52.3219
posterior odds = 0.1 × 52.3219                              =  5.2322
p              = 5.2322 / 6.2322                            =  0.839543
```

| | Value |
|---|---|
| **PRAHARI** | **0.839543 → 0.84** |
| **Naive noisy-OR** `1 − Π(1−sᵢ)` | **0.999126 → 0.999** |
| **Gap** | **0.1596** |
| Trail reproduces `p_raw` exactly | **yes**, to 12 dp |

A score whose trail cannot recompute it is a Critical finding, not a rounding quibble.

### Must-not-link caps

Caps clamp the result rather than subtracting from it, because the reason for a cap is a
*competing explanation*, not a weaker one.

| Flag | Meaning | Ceiling |
|---|---|---|
| `conflicting_pgp` | Two personas signing simultaneously with different keys on the same platform — strong evidence of two people, whatever else agrees | **0.25** |
| `mimicry_suspected` | A copied bio explains the linguistic agreement without any shared author | **0.30** |
| `analyst_reject` | An analyst who looked and said no outranks the model | **0.10** |
| `exchange_wallet` / `mixer_wallet` | Shared by thousands, so not evidence of shared control — the **financial root is dropped entirely**, not downweighted. A weak version of a fact that isn't a fact is still not a fact. | **drop root** |

### Calibration and the guarantee

Isotonic regression on a held-out split gives `p_calibrated`. Split-conformal prediction then
yields, for a risk budget α, a threshold τ such that the false-merge rate among links at
`p ≥ τ` is ≤ α with a distribution-free coverage guarantee. Fixed seed 42, 3,340 pairs,
2,004 train / 1,336 validation.

| α | τ | measured FMR | holds | accepted links |
|---|---|---|---|---|
| 0.01 | 1.000000 | 0.0000 | **yes** | 52 |
| 0.02 | 1.000000 | 0.0000 | **yes** | 52 |
| 0.05 | 0.029851 | 0.031348 | **yes** | 93 |
| 0.10 | 0.029851 | 0.031348 | **yes** | 93 |
| 0.20 | 0.029851 | 0.031348 | **yes** | 93 |

**Stated limitation (DEC-029).** Isotonic collapses these scores into few distinct steps, so
τ has coarse resolution: α = 0.05 and α = 0.10 currently share a τ, and α = 0.01 is only
honourable by accepting the 52 pairs scored at 1.0. That is a limit of 1,336 validation
pairs, not a bug — and the UI slider must not imply finer control than the data supports.

## 6. The audit chain

The claim is narrow and testable: **nobody changed the record after the fact, and we can
prove which analyst made each decision.** Three layers, each defeating a different attacker.

| Layer | Mechanism | Attacker it defeats |
|---|---|---|
| **Canonical JSON** | Sorted keys, no whitespace, UTF-8, no NaN | Two systems that serialise the same record differently — a hash over ambiguous bytes proves nothing |
| **Hash chain** | `hash_n = keccak(prev_hash ‖ leaf_n)` | Editing record *k* breaks every hash from *k* onward, and verification reports the failing **index**, not just "invalid" |
| **Ed25519** | Each record signed by the analyst, key registered at signup | An attacker with full database write access still cannot forge a signature without the private key, which never touches the server |
| **Merkle root** | Per-case tree over sorted leaves, anchored on chain | An operator who would backdate a seal — a root can be anchored exactly once, and re-anchoring reverts |

An odd node in the tree is **promoted, never duplicated**. Duplicating the last node is the
classic CVE-2012-2459 shape, where two distinct leaf sets produce the same root.

The inclusion proof is what makes an export admissible without disclosure: an analyst hands a
court one record plus a short proof, and the court verifies that record was in the sealed
case — without ever seeing the other records, which may concern unrelated suspects. That is
the practical reading of **Bharatiya Sakshya Adhiniyam 2023 §63**.

**Threat model** (attacked adversarially in D3.3): an attacker with *full database write
access* but without the analyst's Ed25519 private key or the anchorer wallet must not be able
to alter, delete, reorder or replay a record undetected.

### The contract

```solidity
// anchor/src/PrahariAnchor.sol — Polygon Amoy, chain id 80002

function anchor(bytes32 root, bytes32 caseRef, uint32 leafCount) external onlyAnchorer;

// reverts on: ZeroRoot · ZeroLeaves · AlreadyAnchored(root) · NotAnchorer
// stores:     Seal { timestamp, leafCount, caseRef, anchorer }
// measured gas: 95,232 on Anvil
```

Sealing is restricted: an open anchor function lets anyone spam roots and destroys the
meaning of "this case was sealed by the cyber cell at this time". Only 32-byte hashes go on
chain. A public blockchain is permanent and world-readable, so putting investigative PII there
would be a far worse privacy failure than the one this system exists to investigate. The
evidence stays on the police network; the chain proves only that it has not changed.

**Pending — user-gated.** The anchorer wallet `0x31EdD0021A09f0B32f7dfeb08B58622c75591991`
needs one free Amoy faucet claim, then `./scripts/deploy_amoy.sh` produces public explorer
links. One claim covers the deploy plus 100+ full demos. Until then the demo runs against
Anvil with a **LOCAL CHAIN** badge — never a silent switch.

## 7. Live Tor timing correlation

Tor hides *which* IP you are, not *when* you send. An adversary who can observe traffic timing
near the client and near the service can line up the two streams and show they are the same
conversation — without decrypting anything. That is the technique that actually unmasks
hidden services in the real world.

| Step | What runs |
|---|---|
| **1 · Backend** | Start a local HTTP backend that timestamps every request it receives — the "service" observation point. |
| **2 · Hidden service** | Launch a tor process via `stem` with an **ephemeral** hidden service mapping onion:80 → that backend. |
| **3 · Client** | Drive a client that fetches the `.onion` through tor's SOCKS proxy on a deliberate timing pattern, timestamping each send — the "client" observation point. |
| **4 · Correlate** | Delay-invariant interval correlation over the two timestamp streams. Returns a confidence and the peak lag, which is the circuit RTT. ~30–40 s end to end. |

Both endpoints are ours, so observing and correlating them is legal and reproducible — a
genuine network-layer result, not a mock. The correlation engine is source-independent: it
takes two timestamp streams and reports how strongly they correlate.

If tor cannot bootstrap — no network, or tor absent — the experiment falls back to a
**controlled replay over the same real correlation engine**, clearly badged `simulated`. The
maths is identical; only the transport differs. **A badge that misreports which path ran is a
Critical finding.**

## 8. Chain flow

Money is the one identifier that has to touch the real world eventually. Two heuristics, both
standard and both defensible in court.

**Common-input clustering.** If a single transaction spends from several addresses at once,
one entity controls all of them — they had to sign for every input. Union-find merges them
into one wallet cluster. This heuristic underpins essentially every real chain-analysis tool.

**Change-address heuristic.** A fresh address receiving the change of a spend is usually
controlled by the same entity. Applied conservatively, only when unambiguous, because a wrong
merge here is a wrong attribution.

Clusters are matched against public exchange and mixer tag lists. A path to a tagged off-ramp
is the real-world lead. A path through a mixer is the money-laundering signal the problem
statement names — and it also **drops the financial evidence for attribution**, because a
mixer output is shared by thousands. Real `mempool.space` data, no API key required.

### The graph intelligence lab

One model in `lib/graphModel.ts`, eleven renderers, plus a hand-rolled **deterministic** force
solver — d3-force seeds from `Math.random` with no way to inject a generator, and an
investigative graph that redraws differently each load is not evidence. Every view exports a
caption stating what its layout *means*. The node inspector shows every edge with its signal
root, strength and reliability exponent, and — uniquely — **what root-cause collapse
discarded**. Export to PNG / SVG / JSON / GraphML, each stamped with actor, filter state,
view, timestamp and engine version.

### The Command Panel

Built security-first, on the rule that a half-secured panel is worse than none.

- **RBAC** — five roles in a strict hierarchy, walked exhaustively by a 351-assertion
  generated matrix.
- **TOTP step-up** — RFC 6238, single-use codes, ±1 drift, hashed single-use recovery codes.
  Destructive actions need a *fresh* 120-second step-up.
- **Sessions** — absolute 8-hour cap, a registry where an unknown session is treated as
  revoked, revoke-all on role change, session-bound CSRF.
- **Passwords** — bcrypt cost 12 + pepper, legacy hashes still accepted, offline breach list.
- **A second, separate proxy** at `/api/admin/[...path]` — `/admin` never enters the read
  proxy's allowlist. The engine then re-verifies a request-bound signed token and re-checks
  the role against its own table.
- **Mutations** — soft-delete only, optimistic concurrency, every one returns its diff and
  lands in the signed ledger. Dry-run-first bulk import; retention purge under a two-person
  rule.

### Generative UI

(`?skin=` → lock → session → fresh draw) with every storage access individually guarded and
an in-memory fallback, so a storage exception cannot break first paint. A floating control
offers three distinct labelled behaviours — Reshuffle, Lock, Unlock — and captions which tier
is in force.

> hex for the DOM and `0xRRGGBB` for three.js from the same source — and a test asserts no

## 10. The engine API

FastAPI, Python 3.12 via `uv`. It boots with no `.env`, with Postgres down, and with every

the generator's identifier-sharing rate would push recall past 0.9 while making the task
strictly easier.

**The authorship verifier.** ROC AUC 0.7976, accuracy 0.7068, 445 train / 191 test pairs.
Learned weights: `char_ngram +3.4000`, `hinglish_diff −3.0039`, `punct_cosine +1.7887`,

**The LLM-rewrite detector.** Burstiness across 244 personas: min 0.102, median 0.205,
max 0.385. An absolute threshold fired on **206 of 244 genuine personas (84% false

genuinely flattened text (burstiness 0.000), and **abstains** when there is no reference
corpus rather than firing anyway.

### Extraction

Perfect scores (P = R = F1 = 1.000) on 30 hand-labelled English and Hinglish sentences — and
the document says why not to quote them naively: the labelled sentences and the alias table
were authored together, so those figures are a **regression guard, not a generalisation
estimate**.

An independent probe of surface forms deliberately absent from the alias table scores
**7/10**, with all three misses being unseen misspellings (`jabalpurr`, `jabalpr`, `JBL`) and
**zero false positives**. That asymmetry is deliberate: matching is exact-alias with no fuzzy
fallback, because a fabricated city manufactures a geofence breach that never happened, and
for a police tool that is strictly worse than missing one. `"kanti"` sits one transposition
from `"Katni"` and must not match. Both directions are pinned by tests.

Over the full **109,689-row** Agora dataset: 0 rows skipped as malformed, **3,192 personas**
extracted, and **1,832 listing bodies (1.67%) dropped as synthesis or how-to content**. The
listing itself is retained — that a vendor offered a category is exactly what we analyse; the
instructions are what we refuse to store or render.

## 13. What is not built

Written down deliberately. A system that publishes its limits is one you can check — that is
the point of the whole design.

### Deliberate non-goals

- It does **not** break Tor. Every source is a public index that already holds the data.
- It does **not** scrape live marketplaces or probe target hosts. Passivity is enforced by a
  network-layer test, not a promise.
- Behavioural analysis runs on **labelled synthetic ground truth**, because the public archive
  we ingest carries no reliable timestamps — stated openly, not buried.
- Stylometry is the **weakest** signal and is weighted at about half a signing key,
  deliberately.

### Declared but unimplemented

| Area | Status |
|---|---|
| Command Panel user CRUD | **Read-only.** Invite / disable / reset-TOTP / revoke-sessions are in the authorisation table but have no handlers — so last-admin protection and self-role-change refusal are *not* implemented, and their tests are **absent rather than vacuously passing**. |
| Persona merge / split | **Not built.** Their ledger actions are reserved. |
| SANGAM Pro layers | **4 of 10.** Certificate reuse, persona overlay, ASN clustering and jurisdiction render their toggles but draw nothing; the temporal scrubber, movement trails and density heat map are absent entirely. |
| `/geo/asn` | **Null ASN.** Cymru's interface is DNS TXT and `dnspython` is not a dependency; the ASN shown in the UI comes from `ipwho.is`. |
| UNAVAILABLE coordinate class | **Unreachable in this data.** No actor in the dataset carries a `.onion`, so it is demonstrated through the host-lookup box instead. |
| Solidity tests | **Not run here.** 12 tests exist; `forge` is not installed in this environment. |
| On-chain anchor | **User-gated.** Needs one free Amoy faucet claim to the anchorer wallet. |
| Phase 7 uptime gate | **Conditional.** Needs a month of real running and the Render usage page, which requires the account owner's login. |

## 15. Free-tier uptime

Figures verified against Render's live documentation on 2026-09-03, not from memory and not
from the plan's assumptions — and the verification changed the design.

| Fact | Verified value |
|---|---|
| Free instance hours | **750 per calendar month** |
| Scope of the pool | **Per workspace, shared** — not per service |
| Spin-down | 15 minutes without inbound traffic |
| Cold start | ~1 minute |
| When hours are consumed | Only while running — spun-down services consume nothing |

```
750 h/month ÷ 3 services                = 250 h per service per month
250 h ÷ 30.44 days                      = 8.21 h per service per day
with the 85% guard: 637.5 ÷ 3 ÷ 30.44   = 6.98 h per service per day

three services awake 24/7 would need 3 × 24 × 30.44 ≈ 2,192 hours
the pool is 750
```

The plan assumed two services and a ~12-hour window. There are **three** sharing one pool, so
the honest window is seven hours, and **no schedule keeps these services up 24/7 on the free
tier**. That is stated rather than worked around.

> **Why the cron is not `*/5`.** It was, and it did not work. Measured over 2026-09-03/04 the
> schedule asked for ~120 runs a day and GitHub delivered **four in two days**. GitHub
> documents `schedule` as best-effort and drops high-frequency crons under load — and against
> Render's fifteen-minute idle timer, a ping every four to nine hours keeps nothing awake.
> What a user saw was the project being down. So the trigger is no longer the thing that has
> to be frequent: **one run holds a single job for a 5.5-hour segment**, ticking every five
> minutes from inside it, then dispatches its own successor. The chain needs the scheduler to
> work *once*, not 120 times a day.

## 16. Degradation contract

Nothing hard-fails. Every dependency has an honest fallback, and the UI always says which path
ran. **A badge that misreports which engine actually ran is a Critical finding.**

| Missing | Behaviour |
|---|---|
| `GROQ_API_KEY` | Local regex extractor; badge says `local` |
| Engine down | DEMO and LIVE modes fully work; DATASET shows "engine offline" |
| Engine *asleep* | Reported as **"waking — a free-tier cold start takes 30–60 s"**, in the same vocabulary in the footer dot and the data panels. Never "offline" |
| `SHODAN_API_KEY` | Infra runs cache-only; crt.sh still carries the 0.95 / 0.85 rules |
| Model weights absent | Stylometry falls back to classic features; the badge says so |
| Network down | Anvil chain + fixtures, with a **LOCAL CHAIN** badge — never a silent switch |
| Tor cannot bootstrap | Controlled replay over the same real correlation engine, badged `simulated` |
| Neo4j / Postgres down | Workbench stays up and degrades honestly |
| `ENGINE_SERVICE_SECRET` | The Command Panel refuses with a 503 that *names the missing variable*, not a bare 500 |

A related rule, from the footer work: **"unknown" is never rendered as "offline"**. A failed
check is a fact about our knowledge, not about the service.
